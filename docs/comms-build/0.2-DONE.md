# 0.2 — One registry of everything that can message a customer

**Built 8 Sep 2026.** Plan v2 week one, item 0.2. Evidence: `data/comms-diagram-verify-s27` §3.1, §3.4,
§3.6, §7.3 · plan-safety-design-s30 F14, F5 · plan-code-feasibility-s29 1.16.

The desk had ONE send gate, `sendCustomerMessage`, and more than thirty callers of it. Eight of those
message a customer with no human tap and no switch at all. One route reached the wire without the gate.
And a paying customer who had once written a plain STOP never received their booking confirmation,
because that message passed no purpose and the gate then read a receipt for money as marketing.

After this item, a customer message cannot leave the system outside one registered, purpose-carrying,
switchable path — and the two concrete holes are shut.

---

## A. The registry — `server/sender-registry.ts`

`server/approver.ts` was already the NAME registry: a closed enum of who may license a send. This file
is the second half of it — for each name, what the send is FOR, whether it can be switched off, and
which class it belongs to.

```ts
Record<AutomatedApprover, { what, purpose, switchKey, kind }>
```

The `Record` over the union is the point: **an approver with no row does not compile.**

| kind | meaning | switchable |
|---|---|---|
| `transactional` | the job requires it; turning it off silently breaks a paid job | **never** |
| `operational` | deterministic policy or a system call site | yes |
| `agent` | an LLM-backed component releasing its own words | yes |

`system.notification` is the one transactional name and it carries all three senders s29 finding 1.16
said must never gain a kill switch: the booking confirmation (`server/email-service.ts`), the
job-lifecycle notifications (`server/customer-notifications.ts:237`) and the Twilio failure-recovery
SMS (`server/whatsapp-api.ts`). Three invariants are checked **at module load**, so a registry that
contradicts itself is a build error, not a runtime surprise:

- a transactional sender carries no switch key;
- every operational and agent sender carries one;
- switch keys are unique.

A person (`human:*`) and a contractor (`contractor:*`) are registered but carry **no registered
purpose**: only the call site knows whether a person is answering a question or starting something, so
the gate's fail-closed `'marketing'` default still applies to a human call site that says nothing.

**The gate now consults it** (`server/outbound.ts`, rule −0.5, immediately after the approver/run-id
check and before anything is spent):

- an approver with no registry row is refused (`SENDER_NOT_REGISTERED` / `reason: 'NOT_REGISTERED'`);
- a sender switched off is refused (`SENDER_SWITCHED_OFF` / `reason: 'SWITCHED_OFF'`);
- the purpose is `input.purpose ?? sender.purpose ?? 'marketing'` — was `input.purpose ?? 'marketing'`.

**This changes no existing call site.** Audited: every one of the ~30 callers of the gate already
states its purpose, `approveAndSendDraft` included (it passes the `purposeForDraftSource(draft.source)`
it enforced two lines earlier). The ONE that did not was the booking confirmation, which is part C
below. The registry's purpose is therefore a net under the next caller, not a re-classification of
anything sending today.

Switches live at `spine.senders.<key>.enabled`, the same `app_settings.spine` row as every other spine
switch, validated by `validateSpineConfigPatch` against the keys the registry actually issued (an
unknown key is a 400: a switch that turns nothing off is the failure this item exists to end). This is
the ONE spine read that **fails open** — absent means on, an unreadable row means on — because the
question here is "may a message someone already composed leave?", and a slow database is not a reason
to drop a customer's invoice.

## B. The composer's bypass — `server/whatsapp-api.ts`

The Meta coexistence transport and the named-template send called `sendWhatsAppMessage` directly: no
approver, no run id, no ledger row, and the release from Ben hand-rolled underneath it. It was the one
route past the gate, and it made the page's own sentence — "cannot send without a named approver and a
run id" — false.

It goes through `sendCustomerMessage` now. `SendCustomerMessageInput` carries `templateName`,
`templateLanguage` and `templateComponents` through to the wire (which already accepted them). The
opt-out check at the top of the route still runs first; `allowSmsFallback: false` keeps the
no-SMS-equivalent rule the old comment stated; the release from Ben happens inside the gate
(`releaseBenAfterHumanSend` → `noteHumanSend`) because the approver is a person.

`server/__tests__/architecture.test.ts` had `server/whatsapp-api.ts` on `SEND_ALLOWED_CALLERS`. It came
off. The wire functions are now reachable from the gate alone.

## C. The blocked confirmation — `server/email-service.ts`

`sendBookingConfirmationWhatsApp` fires on a paid deposit, a quote acceptance or a cash booking and
passed no purpose, so the gate read it as marketing. `conversationEngine.sendMessage` now takes an
optional `purpose` and passes it to the gate; the confirmation states `'service_reply'`. The registry's
own default for `system.notification` is the belt behind it.

Regression test (`server/outbound-registry.test.ts`): with a plain STOP suppression on the number, the
booking confirmation goes out and a marketing send to the same number is still refused.

## D. One silence clock — `server/agents/silence-breaker.ts`

Three lanes ran as three clocks inside one `Promise.all`. They are one behaviour on three triggers.
`runSilenceClock` runs `SILENCE_LANES` — `silence`, `flag_expiry`, `draft_expiry` — sequentially in a
fixed order, each still owning its own scan, its own table and its own claim, all emitting through one
place. **A refactor:** the ten minutes, the 48-hour ceiling, the per-pass caps, the two-hour holding
window in `rules-layer.ts`, the wording and the flag-expiry re-ping to Ben are all untouched. Adding a
fourth trigger is a row, not a fourth clock. `runSilenceBreakerTick` is kept as an alias.

## E. The regulated net — `server/spine/triage.ts`

The rules lexicons read the newest inbound alone. That is right for "call me" or "how much", which are
things the customer is asking now. It is wrong for gas, which is a property of the JOB: a thread whose
first message said "boiler" and whose third says "so can you come Tuesday?" reached no exception, and
gas is the ONE thing T18 leaves as Ben's.

`RE_REGULATED` now reads the last **three** customer texts (`recentCustomerTexts`, `REGULATED_LOOKBACK`)
and every media description on the case file (`mediaDescriptions`) — a photo of a flue is the same fact,
and with `spine.video` on the describer is the only thing that can see it. `regulatedHit` returns WHERE
it fired, so the run's reason line names the message or the photo. It sits outside the `text &&` guard
(a described photo with no words at all is enough) and inside the T21 guard (a message Ben has since
answered on the phone is not re-read).

**Nothing else widened.** The money, callback, refund, complaint and date lexicons still read the newest
message only, and `server/spine/regulated-net.test.ts` says so explicitly.

## F. The test that makes it stick — `server/__tests__/sender-registry.test.ts`

The item's real deliverable. It walks the source tree and asserts:

1. the registry is complete and self-consistent (every approver has a row, the registry names nothing
   that is not an approver, transactional rows carry no switch, every other row does, keys are unique);
2. every call site of `sendCustomerMessage` names a registered sender — a string literal must be in the
   registry, and a non-literal expression must be one of four listed indirections, each with the reason
   it is safe, so a NEW indirection is a failing test and a decision rather than a silent hole (the
   allowlist is also checked for dead entries);
3. `sendWhatsAppMessage` and `sendSmsMessage` are invoked only from `server/outbound.ts`, the composer
   no longer imports the wire at all, the gate really does consult the registry, and the booking
   confirmation really does pass the transactional purpose.

It fails when someone adds an unregistered sender.

## G. The dead switches — **wired, not removed**

`spine.agents.<key>.enabled` was read from exactly one place, `server/spine/agents/scoper-adapter.ts`,
which the live pass does not go through. Every switch on the /admin/staff strip was a label.

Wired, because the plan's direction is more control over what reaches a customer, not less:

- the four lane agents (`scoper`, `quote_clerk`, `recovery`, and `contractor_liaison`, which had no
  switch at all) are stopped in `runOnceBody` via `switchKeyForAgent`;
- the triage MODEL is stopped inside `triage()` — the deterministic rules still run and still raise
  every exception, which is exactly what happens today when the model call fails;
- `verifier` stops the morning sampler's judge calls (`server/spine/sampler.ts`).

Off means the pass **still runs** — case file built, triage's tags written, the run recorded — and
simply proposes nothing, which `decide()` reads as `none`. A switched-off agent says nothing to a
customer; it never falls through to someone else's words. It is not recorded as an error, or every
deliberate "quiet this agent" would read as an incident on the board.

The switches read `isAgentSwitchOn` (`server/spine/config.ts`), **not** `isSpineEnabled`.
`isSpineEnabled` also reads the master switch, which is the right question for a caller deciding
whether to START a pass and the wrong one for a pass already running: the shadow runner and the sandbox
(`server/spine/sandbox-routes.ts`) call `runOnce` directly with the master switch off by design, and
reading it inside the pass would have silenced every agent in the sandbox the moment the spine was not
live.

## What was NOT verified live

No `.env`, no database, no API, no UI here. Everything above is verified by tests, by type-checking and
by reading the code. Specifically **not** observed: a real Meta template send through the new gate path;
a real booking confirmation reaching a suppressed number; the /admin/staff strip rendering; a real
switched-off agent on a live thread.

**One behavioural edge, stated rather than special-cased.** The composer's Meta/template route now
enters the gate, so a UK **landline** on that route takes the gate's landline rule and goes out as SMS
with the same words, where it previously attempted Meta and failed. The non-Meta composer route has
always behaved that way, a landline can never be a WhatsApp coexistence contact, and the route already
rejects an empty body — so the customer gets the words instead of a silent failure. (Related: the old
route returned `messageId: result.messages?.[0]?.id`, which was always `undefined` — the Meta wire
returns `{ sid, status }`. It now returns the real sid.)
