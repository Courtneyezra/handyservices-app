## The gap

`startHeartbeatStaleCheck()` returned immediately unless `isCommsWorker()`
(`server/comms-worker-heartbeat.ts`, the guard s29 1.6 cites at `:210-213`). So the stale-heartbeat
alarm lived **inside the process it was watching**: a *wedged* worker — one whose timers still run
but whose DB writes fail — pages Ben, and a *dead* one pages nobody at all. The web process already
read the heartbeat for `/api/health/comms-worker` (`server/index.ts:271`) and did nothing with what
it read.

That matters more here than in most systems, because every customer-facing clock in the desk is
worker-only: the passes themselves, the rules layer's holding lines, the chase ladder. A dead worker
is not a degraded desk. It is a silent one, and today nobody finds out. Once replies send by
default (WS1), it is silence with no queue of drafts to show for it either.

## What changed

**One new alarm, outside the worker.** `checkHeartbeatFromOutsideOnce()` in
`server/comms-worker-heartbeat.ts` is the same check the worker runs on itself, run from a process
that is **not** the worker. `startHeartbeatWatchdog()` registers it on its own `setInterval` (the
existing `STALE_CHECK_EVERY_MS`, 5 min) and is called once from `server/index.ts`, next to the
Phase 0 boot check. Same push path as the alarm inside (`notifyWorkerHealth` → the `worker_health`
Pushover key), same wording style, same throttle (one page an hour), same UK daytime window
(08–20) — a stale worker overnight still waits for the morning, as it always has.

**The two alarms can never fire for the same episode.** `shouldAlertStale` requires
`isWorker`; the new `shouldWatchdogAlert` is its mirror image and requires the opposite. A process
is one or the other for its whole life, so no process satisfies both, and no pair of processes
double-pages: the worker only ever speaks about itself, and only a non-worker speaks about the
worker's absence. A test asserts the mirror directly.

**Recovery is not silent.** Once the watchdog has paged, the first fresh heartbeat sends exactly one
`comms worker is back`, naming how long the silence lasted and telling Ben to check the desk for
what queued. If the episode never paged (a blip out of hours), nothing is announced — a recovery
message for an outage nobody was told about is noise.

**A laptop never pages.** The watchdog also requires `NODE_ENV=production`. A dev process on a Neon
branch is passive and has never seen a heartbeat row, which is correct and not an alarm; without
this belt every local `npm run dev` would page Ben once an hour.

**The health endpoint says so in one word.** `getHeartbeatHealth()` now carries
`status: 'ok' | 'stale'` alongside the existing `ok` / `stale` / `ageSeconds`. The endpoint's
status codes are unchanged (they were already right); the field is there so a platform healthcheck
or an uptime monitor can read one field rather than infer.

### What `GET /api/health/comms-worker` returns, state by state

| state | HTTP | body |
|---|---|---|
| heartbeat fresh (≤ 10 min old) | **200** | `status: "ok"`, `ok: true`, `stale: false`, `ageSeconds: <n>`, plus `at` / `pid` / `host` / `version` of the worker that stamped it, `thisProcess` (the process answering), `staleAfterSeconds: 600`, `skippedLoopsInThisProcess` |
| heartbeat older than 10 min | **503** | `status: "stale"`, `ok: false`, `stale: true`, `ageSeconds: <n>`, the stamping worker's `at` / `pid` / `host` |
| never written (no row) | **503** | `status: "stale"`, `ok: false`, `stale: true`, `ageSeconds: null`, `at: null` |
| row unreadable (DB down, no `DATABASE_URL`) | **503** | as above plus `error: "heartbeat unreadable: <reason>"` |
| the health module itself fails to load | **503** | `status: "stale"`, `ok: false`, `stale: true`, `error: <reason>` |

A platform healthcheck can use the status code alone; anything richer reads `status`.

## Tests

`npx vitest run server/comms-worker-heartbeat.test.ts` → **24 passed**. The new ones:

- a stale heartbeat pages once, with the title `comms worker is not running`;
- a fresh heartbeat is silent, and so is one exactly at the 600 s boundary;
- a second poll five minutes in, and one a second short of the hour, do **not** page again;
- an hour later, still dead, pages a second time;
- recovery pages exactly once (`comms worker is back`, "silent for about 20 min") and the next fresh
  poll says nothing;
- an outage that never paged (out of hours) announces no recovery;
- the check is **inert in the worker** (`is-worker`, no push, `startHeartbeatWatchdog()` false) and
  inert on a laptop (`not-production`), and registers exactly one timer in a passive production
  process;
- `shouldWatchdogAlert` is the mirror image of `shouldAlertStale` on the role field — the same input
  that pages one silences the other;
- a push that throws does not break the pass;
- `getHeartbeatHealth` reports `status: "stale"` with the reason when the row cannot be read.

## What could not be verified here, and the one thing the captain must decide

- **No live proof.** No database, no Pushover token: no page was sent and no heartbeat row was read
  on this machine. The alarm's push path is the existing `notifyWorkerHealth`, unchanged.
- **Today production is one Railway service that is both the web process and the worker**
  (`docs/comms-build/PHASE0-OPS.md` §1: `COMMS_WORKER=1` on service `handyservices-app`). The
  watchdog is inert in the worker by design, so **on today's single-service deployment nothing is
  watching from outside yet**. The code is correct and lands the alarm the moment a passive
  production process exists; until then the covering path is item 4 of the brief — the platform
  healthcheck on the 503 from `/api/health/comms-worker`, which is what `PHASE0-OPS.md` §5's last
  line already asks for and which this PR documents state by state.
  Two ways to close it, both ops rather than code, and the captain's call:
  1. point Railway's healthcheck (or an external uptime monitor) at `/api/health/comms-worker` on
     the worker service, so the platform restarts or alerts on the 503; **or**
  2. run a second, tiny Railway service from the same image **without** `COMMS_WORKER=1` — it serves
     nothing customer-facing, and this watchdog then pages from outside as designed.
- The UK 08–20 window was kept because that is the existing alarm's behaviour and nothing recorded
  changes it. If a dead desk should page at 03:00 once replies send unattended, that is a one-line
  change and a decision, not a bug.
