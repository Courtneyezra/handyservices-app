# 0.7 — DONE: no prompt change without its test; the scoreboard on the server

Build plan v2, WS0 item 0.7. Two findings, one item.

- **The evidence link was dead in production.** The daily promotion job reads its eval evidence
  from `eval-results/latest.json` on the worker's filesystem. `eval-results/` is gitignored
  (`.gitignore:67`) and the container build has no step that runs the harness, so on Railway the
  file has never existed: every intent's `evalFamily` read `missing`, and only the two fast-tracked
  intents (`ask_gap`, `confirm_received`) could ever be promoted. The evidence half of the
  earned-autonomy design had never once run. (s31 §2.2, §5.1; s29 finding 1.7.)
- **Nothing gated a prompt change.** Five items of the plan rewrite the Scoper's standing orders,
  and the only conversation-level proof this desk has is a person driving the sandbox by hand.

Nothing about **what** the job promotes or demotes changed. 0.7 changes where it reads its evidence
from, and adds a check that refuses a prompt change with no test beside it.

## A. The scoreboard in the database

| Where | What |
|---|---|
| `shared/schema.ts` `evalRuns` + `migrations/20260908_eval_runs.sql` | one row per harness run: `run_id`, `git_ref`, `prompt_hash`, `prompt_hashes`, `adapters`, `families` (per family `{ cases, graded, green, red }`), the red counts, `finished_at`. Unique on `run_id`, so a re-publish updates rather than duplicates. |
| `server/evals/eval-run-store.ts` | `familyCountsOf` (pure) counts a family EXACTLY as `evalFamilyFrom` counts the file's `cases[]`, so the two evidence paths cannot disagree; `evalRunRecord` (pure) is the row; `saveEvalRun` writes it and never throws; `latestEvalRunRow` reads the newest, or null with no database. |
| `scripts/eval-comms.ts` | writes the row as well as the file, **only when a real `DATABASE_URL` was in the environment** (captured before the harness's own placeholder). With no database the run is byte-for-byte what it was: the file is written, the table is skipped, and the line says so. `--no-publish` skips it deliberately. |
| `server/spine/autonomy.ts` | `readLatestScoreboard` is now async and reads the **table first, the file second, nothing third**. `readScoreboardFile` is the old sync file read, kept. `EvalFamilyStatus` gained `source` (`db` \| `file` \| `none`) and `promptHash`. |

**With neither a row nor a file the status is `missing`** — the same reading as before 0.7, and the
same one the full gate refuses to promote on. There is no path on which an absent scoreboard reads
as green.

**How the table gets its first row on the server.** Nothing in the container build runs the evals,
and 0.7 does not add an eval step to the build (the spine adapter needs a model key and costs money
per run; that is not a thing to do on every deploy). It is a one-liner a person runs, with the
migration applied first:

```bash
npx tsx scripts/_apply-migration.ts migrations/20260908_eval_runs.sql
DATABASE_URL=<the server's> npx tsx scripts/eval-comms.ts                    # grades and publishes
DATABASE_URL=<the server's> npx tsx scripts/_eval-scoreboard.ts --publish    # or publish a latest.json you already have
npx tsx scripts/_eval-scoreboard.ts --status                                 # what the job would read, and from where
```

The replay and triage adapters need no key, so step two is free; a `--adapter spine` run against the
model is what actually earns a family its green.

## B. The prompt gate

**The rule.** A change under `server/spine/prompts/` must arrive with a change under `eval-cases/`.
Pure, in `server/evals/prompt-gate.ts`; the message names the prompt that moved and says its eval
family is missing.

**Where it runs.** `npm run gate:prompts` locally (`scripts/check-prompt-gate.ts`, diffing the merge
base plus the working tree), and `.github/workflows/prompt-gate.yml` on every pull request.

> This is the repository's **first** GitHub Actions workflow. The four checks a pull request runs
> today are Vercel's — three preview deployments plus preview comments. They build the app; they do
> not test it. There was no test CI to extend, so this adds the smallest possible one (one script,
> `npx tsx`, no dependency install) rather than a parallel test runner.

**The budget**, in `docs/RUNBOOK.md` §"Changing a prompt": a family is 5–10 cases × 3 trials, a
Scoper run is roughly 8k in / 1k out on Sonnet ($2 / $10 per M, `server/agent-cost.ts`) ≈ 2p, so
**£0.30–£0.60 a family** and **£5–£8** for every intent family at once. Estimated from token sizes,
not measured; the run prints its own usage.

## C. Prompt provenance

`server/evals/prompt-provenance.ts` records two things on every eval run, file and table alike:

- `promptHash` — one digest over `server/spine/prompts/*`. Any prompt edit moves it, so a stale
  green is visible: `scripts/_eval-scoreboard.ts --status` prints **STALE** when the digest the
  scoreboard graded is not the digest of the prompts you are reading.
- `promptHashes` — the Scoper's **own** per-pack hash, the identical value
  `promptHashOf(buildScoperSystem(pack))` that lands on `agent_runs.prompt_hash`, so an eval result
  and a production run can be matched exactly.

Recorded and shown; **not** gated on. Promotion and demotion rules are out of scope for 0.7.
